# Графика

## API

Всё, что рисуется, проходит через функции `w3dEngine` (`graphics/w3dGraphics.h`): включение и выключение возможностей (`Enable`, `Disable`), матрицы (`MatrixMode`, `PushMatrix`, `Translatef`, `Perspective`), массивы вершин (`VertexPointer3f`, `NormalPointer3b`, `TexCoordPointer2f`), буферы на GPU (`GenBuffer`, `ArrayBufferData`), рисование (`DrawTriangles`, `DrawLines`, `DrawPoints`), материалы (`Material`), источники света (`LightNfv`, `LightNSpot`), туман, смешивание, отсечение прямоугольником, трафарет и плоскости отсечения.

Он намеренно похож на классический OpenGL: это способ рисования, который понимает больше всего систем, от N95 до Dreamcast.

## Фиксированный конвейер и шейдеры

Есть два семейства GPU:

- **Фиксированный конвейер.** В GPU шаги заложены с завода: преобразование вершин, расчёт освещения по вершинам, наложение текстуры, туман. Программа только включает переключатели и передаёт значения. Так работают OpenGL ES 1.1 (N95), классический OpenGL на ПК, GE в PSP и PVR в Dreamcast.
- **Шейдеры.** В GPU ничего не заложено: каждый шаг — это маленькая программа, которая выполняется на ней. Так работают OpenGL ES 2.0, WebGL и Vulkan.

Core говорит на языке фиксированного конвейера. Бэкенд шейдеров **эмулирует** его с помощью «убер-шейдера», который делает те же вычисления, что и OpenGL ES 1.1 (освещение по вершинам до 8 источников, затухание, конус, туман, смешивание двух текстур). Поэтому в браузере и на Android всё выглядит так же, как на ПК и N95.

## Бэкенды

| Бэкенд | Что это | Где используется |
|---|---|---|
| `opengl/` | Фиксированный конвейер: настольный OpenGL, OpenGL ES 1.1, GLdc, vitaGL | Linux, Windows, macOS, N95 и S60, Dreamcast, PS Vita |
| `gles2/` | Шейдеры: OpenGL ES 2.0 и WebGL | Android, браузер, Nokia N8 (Symbian^3), ПК (по желанию) |
| `vulkan/` | Тот же бэкенд шейдеров, собранный поверх OpenGL ES 2.0, реализованного на Vulkan | ПК (по желанию) |
| `gu/` | GE в PSP | PSP |
| `citro3d/` | GPU PICA200 в 3DS | Nintendo 3DS |
| `pvr/` | Прямое рисование на PVR в Dreamcast | Необязательный модуль для нативных игр |
| `video/` | Видео в текстуру | Необязательно: FFmpeg на десктопе, `<video>` в браузере |

## Как выбирается

Почти всегда — **при сборке**: каждая система собирает только один бэкенд, и вызовы идут напрямую, без дополнительных затрат.

Исключение — ПК (Windows и Linux). Там исполняемый файл содержит OpenGL, OpenGL ES 2.0 и Vulkan, а выбор делается **при запуске**, в **Свойства → Настройки → Графика** (вступает в силу после перезапуска; см. [Другие функции](../editor/otras-funciones.md)). Каждый бэкенд собирается в своём пространстве имён (`w3dEngine::gl`, `w3dEngine::es2`, `w3dEngine::vk`) и заполняет своими функциями **таблицу диспетчеризации** (`w3dBackendTabla.h`). Каждая функция `w3dEngine` вызывает функцию активного бэкенда:

```cpp
// graphics/w3dDespacho.inc, генерируется tools/generar_despacho.py
void Enable(Cap c) { W3D_TABLA()->Enable(c); }
void DrawTriangles(int count, const MeshIndex* indices) { W3D_TABLA()->DrawTriangles(count, indices); }
```

Если выбранный бэкенд не работает на этой машине, остаётся OpenGL. Vulkan нужны драйвер, GPU и компилятор шейдеров `shaderc_shared` рядом с исполняемым файлом, а в 32-битных сборках он выключен. В macOS исполняемый файл содержит только OpenGL.

## Путь одного `DrawTriangles`

Один и тот же запрос заканчивается в совершенно разных местах:

![Один и тот же gfx::DrawTriangles проходит через Whisk3D Core и спускается в каждый бэкенд: opengl (ПК, macOS, N95, Dreamcast, PS Vita), gles2 (Android, браузер, N8, ПК), vulkan (ПК), gu (PSP) и citro3d (3DS)](img/whisk3d-core-despacho.webp)

- **Фиксированный OpenGL (ПК, N95):** почти напрямую в `glDrawElements`. Матрица отправляется только перед рисованием, одним `glLoadMatrixf`.
- **OpenGL ES 2.0 и WebGL:** стек матриц живёт на CPU и передаётся как uniform-переменные в убер-шейдер. WebGL не принимает массивы из RAM, поэтому бэкенд переносит их в буферы. На GPU VideoCore IV в Android 2.3 он собирает маленькую программу для каждой комбинации состояния и объединяет вызовы рисования интерфейса: из 179 за кадр остаётся 16.
- **PSP (GE):** CPU переводит каждую вершину в пространство отсечения и отсекает там, потому что GE не отсекает по боковым сторонам. Затем вершины записываются вперемешку в кольцевой буфер памяти, который читает GE. Освещение (до четырёх источников) и туман идут аппаратно.
- **3DS (PICA200):** вершины копируются в линейную память, а преобразует их собственный вершинный шейдер (`w3d.v.pica`). Небольшие вызовы рисования подряд с одинаковым состоянием отправляются вместе: из 191 за кадр остаётся 18. Линии и точки строятся на CPU как треугольники.
- **Dreamcast:** GLdc играет роль OpenGL 1.x поверх PVR и использует тот же фиксированный бэкенд, что ПК и N95, с собственными патчами. Для игры, которой нужен каждый такт, есть `pvr/`: GLdc тратит около 400 тактов SH-4 на вершину, а прямое рисование преобразует каждую одной инструкцией (`FTRV`). В одной программе они не уживаются.
- **PS Vita:** vitaGL эмулирует фиксированный конвейер на GPU консоли и компилирует свои шейдеры во время работы (поэтому ему нужен `libshacccg.suprx`).

## Спросить у бэкенда, что он умеет

Не все GPU умеют одно и то же, и Core этого не скрывает: каждый бэкенд сообщает, что у него есть, а тот, кто рисует, выбирает другой путь, если чего-то не хватает.

| Вопрос | Что происходит, если ответ «нет» |
|---|---|
| `VBOSoportado()` | Меши передаются как массивы в RAM (Dreamcast, Vita) |
| `EstencilBits()` | Отражение воды переходит на отсечение плоскостями |
| `PlanosRecorteMax()` | Отражение обходится без плоскостей (у PVR их нет) |
| `MezclaTexturasSoportada()` | Слои материала рисуются в несколько проходов |
| `TieneTexGen()` | Сферическое отражение вычисляется программно или текстурной матрицей (`TexMatrixMatcap`, которая работает и на N95) |
| `SombreadoPorPixelSoportado()` | Освещение остаётся повершинным, и редактор даже не предлагает эту опцию |
| `ShadersEscritos()` | Материал со своим шейдером рисуется как обычно (см. [Свои шейдеры](../editor/shaders.md)) |

## Кэш состояния

Каждое изменение состояния чего-то стоит драйверу. Core помнит, что сейчас установлено: включение того, что уже включено, или привязка уже привязанной текстуры не порождает ни одного вызова. `IsEnabled` и `GetMatrix` отвечают из этой памяти и не спрашивают GPU, потому что на N95 такой вопрос заставляет ждать, пока она закончит рисовать.

## Текстуры

У `LoadTexture` два шага. **Декодирование** (из файла в пиксели RGBA) зависит от системы: почти везде stb, в Symbian — ICL. **Загрузка** (из пикселей в GPU) общая, и каждый бэкенд переводит данные в формат своего чипа:

- **PSP:** степень двойки до 512, «swizzled», в 565 или 8888.
- **3DS:** блоки 8x8 в порядке Мортона, от 8 до 1024 по стороне.
- **Dreamcast:** степень двойки от 8 до 1024, в 16 битах (565 или 4444), без mipmap-уровней.
- **N95:** только степень двойки; остальные размеры перед загрузкой масштабируются.

Проект может запросить текстуры в **16 бит** (вдвое меньше памяти) и, только на N95, загружать их **в половинном размере** начиная с определённого размера (`texturasMitadDesde`). Формат `.w3dt` хранит текстуру, уже готовую для GPU, с mipmap-уровнями: загрузить её — значит прочитать и отправить в GPU.

Честная деталь: загрузка текстур и освещение пока ещё напрямую вызывают две-три функции OpenGL. На консолях без OpenGL бэкенд содержит небольшую прослойку, которая их реализует (`gu/w3dGLgu.cpp`, `citro3d/w3dGLc3d.cpp`).

## Экран и безопасная область

`PantallaSetTam` и `PantallaEsVertical` один раз запоминают, стоит экран вертикально или лежит горизонтально (горизонтально = шире, чем выше), чтобы любая часть движка могла это узнать. **Безопасная область** (`SafeAreaGet`) говорит, сколько пикселей с каждого края нельзя использовать для интерфейса: вырез, полоса жестов, панели браузера на телефоне. Фон рисуется на всё окно, а интерфейс — внутри безопасной области. На ПК, в Symbian и на консолях края равны 0; в браузере они измеряются.

## Ограничения самой слабой машины

То, что пишется для Core, должно помещаться в самую ограниченную машину. Вот ограничения, которые заметны:

| Ограничение | Где | Как Core с ним справляется |
|---|---|---|
| 16-битные индексы (до 65 535 вершин на меш) | Symbian | `MeshIndex` там 16-битный, а в остальных системах 32-битный; импортёр отклоняет то, что не помещается |
| 8 источников света одновременно | Все (`LucesMax`) | Бэкенд шейдеров эмулирует их тем же расчётом; PSP делает 4 аппаратно, а Android 2.3 использует до 4 |
| Без шейдеров | Фиксированные бэкенды | Функции шейдеров отвечают «нет», и материал рисуется как обычно |
| 16-битный Z | PSP | Ближняя плоскость подстраивается под расстояние орбиты, как на N95 |
| 16 МБ на всё | Dreamcast | Сборка с `-Os`, и компоновщик выбрасывает неиспользуемое; текстуры идут в 16 битах |
| C++03 | Symbian | Никаких `nullptr`, `auto` и `override` в заголовках (`W3D_OVERRIDE`); `tools/prueba_independencia.sh` компилирует каждый заголовок отдельно, в C++03 |
