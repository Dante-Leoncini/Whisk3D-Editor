# Graphics

## The API

Everything that gets drawn goes through the `w3dEngine` functions (`graphics/w3dGraphics.h`): turning capabilities on and off (`Enable`, `Disable`), matrices (`MatrixMode`, `PushMatrix`, `Translatef`, `Perspective`), vertex arrays (`VertexPointer3f`, `NormalPointer3b`, `TexCoordPointer2f`), GPU buffers (`GenBuffer`, `ArrayBufferData`), drawing (`DrawTriangles`, `DrawLines`, `DrawPoints`), materials (`Material`), lights (`LightNfv`, `LightNSpot`), fog, blending, rectangle clipping, stencil and clip planes.

It looks like classic OpenGL on purpose: it's the way of drawing that the most systems understand, from the N95 to the Dreamcast.

## Fixed pipeline and shaders

There are two families of GPU:

- **Fixed pipeline.** The GPU comes with the steps built in at the factory: transforming the vertices, computing per-vertex lighting, combining the texture, adding fog. The program only flips switches and passes values. This is how OpenGL ES 1.1 (the N95), classic OpenGL on PC, the PSP's GE and the Dreamcast's PVR work.
- **Shaders.** The GPU comes with nothing built in: each step is a small program that runs on it. This is how OpenGL ES 2.0, WebGL and Vulkan work.

The Core speaks the fixed pipeline's language. The shader backend **emulates** it with an "uber-shader" that does the same math as OpenGL ES 1.1 (per-vertex lighting with up to 8 lights, attenuation, cone, fog, blending two textures). That's why the browser and Android look the same as the PC and the N95.

## The backends

| Backend | What it is | Where it's used |
|---|---|---|
| `opengl/` | Fixed pipeline: desktop OpenGL, OpenGL ES 1.1, GLdc, vitaGL | Linux, Windows, macOS, N95 and S60, Dreamcast, PS Vita |
| `gles2/` | Shaders: OpenGL ES 2.0 and WebGL | Android, the browser, the Nokia N8 (Symbian^3), PC (optional) |
| `vulkan/` | The same shader backend, compiled on top of an OpenGL ES 2.0 implemented with Vulkan | PC (optional) |
| `gu/` | The PSP's GE | PSP |
| `citro3d/` | The 3DS's PICA200 GPU | Nintendo 3DS |
| `pvr/` | Direct drawing to the Dreamcast's PVR | Optional module for native games |
| `video/` | Video to texture | Optional: FFmpeg on desktop, `<video>` in the browser |

## How it's chosen

Almost always **at compile time**: each system compiles a single backend and the calls go straight to it, with no extra cost.

The exception is the PC (Windows and Linux). There the executable carries OpenGL, OpenGL ES 2.0 and Vulkan, and you choose **at startup**, in **Properties → Settings → Graphics** (it applies after restarting; see [Other functions](../editor/otras-funciones.md)). Each backend is compiled in its own namespace (`w3dEngine::gl`, `w3dEngine::es2`, `w3dEngine::vk`) and fills a **dispatch table** (`w3dBackendTabla.h`) with its functions. Each `w3dEngine` function calls the active backend's one:

```cpp
// graphics/w3dDespacho.inc, generated by tools/generar_despacho.py
void Enable(Cap c) { W3D_TABLA()->Enable(c); }
void DrawTriangles(int count, const MeshIndex* indices) { W3D_TABLA()->DrawTriangles(count, indices); }
```

If the chosen one doesn't work on that machine, it falls back to OpenGL. Vulkan needs the driver, the GPU and the `shaderc_shared` shader compiler next to the executable, and it's turned off in 32-bit builds. On macOS the executable carries only OpenGL.

## The journey of a `DrawTriangles`

The same request ends up in very different places:

![The same gfx::DrawTriangles goes through Whisk3D Core and down to each backend: opengl (PC, macOS, N95, Dreamcast, PS Vita), gles2 (Android, browser, N8, PC), vulkan (PC), gu (PSP) and citro3d (3DS)](img/whisk3d-core-despacho.webp)

- **Fixed OpenGL (PC, N95):** almost straight to `glDrawElements`. The matrix is sent only right before drawing, in a single `glLoadMatrixf`.
- **OpenGL ES 2.0 and WebGL:** the matrix stack lives on the CPU and travels as uniforms to the uber-shader. WebGL doesn't accept arrays in RAM, so the backend moves them into buffers. On the VideoCore IV GPU of Android 2.3 it builds a small program per state combination and batches the interface's draws: 179 per frame become 16.
- **PSP (GE):** the CPU takes each vertex to clip space and clips there, because the GE doesn't clip against the sides. Then it writes them interleaved into a memory ring that the GE reads. Lighting (up to four lights) and fog are done in hardware.
- **3DS (PICA200):** the vertices are copied to linear memory and transformed by a custom vertex shader (`w3d.v.pica`). Consecutive small draws with the same state go out together: 191 per frame become 18. Lines and points are built on the CPU as triangles.
- **Dreamcast:** GLdc acts as OpenGL 1.x on top of the PVR and uses the same fixed backend as the PC and the N95, with its own patches. For a game that needs every cycle there's `pvr/`: GLdc spends about 400 SH-4 cycles per vertex, and direct drawing transforms each one with a single instruction (`FTRV`). They can't live in the same program.
- **PS Vita:** vitaGL emulates the fixed pipeline on the console's GPU and compiles its shaders at runtime (that's why it needs `libshacccg.suprx`).

## Asking the backend what it can do

Not every GPU can do the same things, and the Core doesn't hide it: each backend answers what it has, and whoever draws takes another path if something is missing.

| Question | What happens if it says no |
|---|---|
| `VBOSoportado()` | Meshes go as arrays in RAM (Dreamcast, Vita) |
| `EstencilBits()` | Water reflections fall back to plane clipping |
| `PlanosRecorteMax()` | Reflections make do without planes (the PVR doesn't have them) |
| `MezclaTexturasSoportada()` | A material's layers are drawn in several passes |
| `TieneTexGen()` | Sphere-map reflections are computed in software or with the texture matrix (`TexMatrixMatcap`, which does work on the N95) |
| `SombreadoPorPixelSoportado()` | Lighting stays per vertex and the editor doesn't even offer the option |
| `ShadersEscritos()` | A material with its own shader is drawn as usual (see [Hand-written shaders](../editor/shaders.md)) |

## The state cache

Every state change costs the driver something. The Core remembers what's set: turning on something that's already on, or binding the texture that's already bound, makes no call at all. `IsEnabled` and `GetMatrix` answer from that memory and don't ask the GPU, because on the N95 a query like that forces it to wait until drawing finishes.

## Textures

`LoadTexture` has two steps. The **decode** (from the file to RGBA pixels) depends on the system: stb on almost all of them, the ICL on Symbian. The **upload** (from the pixels to the GPU) is shared, and each backend converts to its chip's format:

- **PSP:** power of two up to 512, "swizzled", in 565 or 8888.
- **3DS:** 8x8 blocks in Morton order, from 8 to 1024 per side.
- **Dreamcast:** power of two from 8 to 1024, in 16 bits (565 or 4444), no mipmaps.
- **N95:** power of two only; the rest are resampled before uploading.

A project can ask for **16-bit** textures (half the memory) and, only on the N95, upload them at **half size** above a certain size (`texturasMitadDesde`). The `.w3dt` format stores a texture already prepared for the GPU, with its mipmaps: loading it means reading and uploading.

An honest detail: texture uploading and lights still call two or three OpenGL functions directly. On consoles without OpenGL, the backend brings a small layer that implements them (`gu/w3dGLgu.cpp`, `citro3d/w3dGLc3d.cpp`).

## The screen and the safe area

`PantallaSetTam` and `PantallaEsVertical` store, just once, whether the screen is upright or lying down (landscape = wider than tall), so any part of the engine can ask. The **safe area** (`SafeAreaGet`) says how many pixels on each edge can't be used for the interface: the notch, the gesture bar, the mobile browser's bars. The background is drawn over the whole window and the interface inside the safe area. On PC, Symbian and the consoles the edges are 0; in the browser they're measured.

## The limits of the smallest

What's written for the Core has to fit on the most limited machine. These are the limits you'll notice:

| Limit | Where | How the Core handles it |
|---|---|---|
| 16-bit indices (up to 65,535 vertices per mesh) | Symbian | `MeshIndex` is 16 bits there and 32 everywhere else; the importer rejects what doesn't fit |
| 8 lights at a time | All (`LucesMax`) | The shader backend emulates them with the same math; the PSP does 4 in hardware and Android 2.3 uses up to 4 |
| No shaders | The fixed backends | The shader functions answer no and the material is drawn as usual |
| 16-bit Z | PSP | The near plane adjusts to the orbit distance, like on the N95 |
| 16 MB for everything | Dreamcast | It's compiled with `-Os` and the linker drops what isn't used; textures are 16-bit |
| C++03 | Symbian | No `nullptr`, `auto` or `override` in the headers (`W3D_OVERRIDE`); `tools/prueba_independencia.sh` compiles each header on its own, in C++03 |
