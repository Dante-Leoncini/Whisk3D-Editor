# グラフィックス

## API

描画するものはすべて、`w3dEngine`（`graphics/w3dGraphics.h`）の関数を通ります：機能のオン・オフ（`Enable`、`Disable`）、行列（`MatrixMode`、`PushMatrix`、`Translatef`、`Perspective`）、頂点配列（`VertexPointer3f`、`NormalPointer3b`、`TexCoordPointer2f`）、GPU上のバッファー（`GenBuffer`、`ArrayBufferData`）、描画（`DrawTriangles`、`DrawLines`、`DrawPoints`）、マテリアル（`Material`）、ライト（`LightNfv`、`LightNSpot`）、フォグ、ブレンド、矩形によるクリッピング、ステンシル、クリッピング平面。

あえて従来のOpenGLに似せています。N95からDreamcastまで、最も多くのシステムが理解できる描画方法だからです。

## 固定パイプラインとシェーダー

GPUには2つの系統があります：

- **固定パイプライン。** GPUには、あらかじめ組み込まれた処理の手順があります：頂点の変換、頂点ごとのライティングの計算、テクスチャの合成、フォグ。プログラムはスイッチを入れて値を渡すだけです。OpenGL ES 1.1（N95）、PCの従来のOpenGL、PSPのGE、DreamcastのPVRがこの方式です。
- **シェーダー。** GPUには何も組み込まれていません。各手順が、GPU上で動く小さなプログラムです。OpenGL ES 2.0、WebGL、Vulkanがこの方式です。

Coreは固定パイプラインの言葉で話します。シェーダーのバックエンドは、OpenGL ES 1.1と同じ計算（最大8個のライトによる頂点ごとのライティング、減衰、コーン、フォグ、2枚のテクスチャの合成）をする「ウーバーシェーダー」で、それを**エミュレート**します。そのため、ブラウザーやAndroidでも、PCやN95と同じ見た目になります。

## バックエンド

| バックエンド | 内容 | 使われる場所 |
|---|---|---|
| `opengl/` | 固定パイプライン：デスクトップのOpenGL、OpenGL ES 1.1、GLdc、vitaGL | Linux、Windows、macOS、N95とS60、Dreamcast、PS Vita |
| `gles2/` | シェーダー：OpenGL ES 2.0とWebGL | Android、ブラウザー、Nokia N8（Symbian^3）、PC（オプション） |
| `vulkan/` | 同じシェーダーのバックエンドを、Vulkanで作ったOpenGL ES 2.0の上でコンパイルしたもの | PC（オプション） |
| `gu/` | PSPのGE | PSP |
| `citro3d/` | 3DSのGPU、PICA200 | Nintendo 3DS |
| `pvr/` | DreamcastのPVRへの直接描画 | ネイティブゲーム用のオプションのモジュール |
| `video/` | 動画をテクスチャに | オプション：デスクトップではFFmpeg、ブラウザーでは`<video>` |

## 選び方

ほとんどの場合、**コンパイル時**に決まります。各システムはバックエンドを1つだけコンパイルし、呼び出しは直接そこへ行くので、余分なコストは一切かかりません。

例外はPC（WindowsとLinux）です。PCの実行ファイルにはOpenGL、OpenGL ES 2.0、Vulkanが入っていて、**起動時**に選びます。選ぶ場所は**Properties → Settings → Graphics**です（再起動後に有効になります。[3D Viewportのその他の機能](../editor/otras-funciones.md)を参照）。各バックエンドはそれぞれの名前空間（`w3dEngine::gl`、`w3dEngine::es2`、`w3dEngine::vk`）でコンパイルされ、自分の関数で**ディスパッチテーブル**（`w3dBackendTabla.h`）を埋めます。`w3dEngine`の各関数は、アクティブなバックエンドの関数を呼び出します：

```cpp
// graphics/w3dDespacho.inc、tools/generar_despacho.pyが生成
void Enable(Cap c) { W3D_TABLA()->Enable(c); }
void DrawTriangles(int count, const MeshIndex* indices) { W3D_TABLA()->DrawTriangles(count, indices); }
```

選んだものがそのマシンで動かなければ、OpenGLのままになります。Vulkanには、ドライバー、GPU、そして実行ファイルの隣にシェーダーコンパイラー`shaderc_shared`が必要で、32ビットのビルドでは無効になっています。macOSの実行ファイルにはOpenGLしか入っていません。

## `DrawTriangles`の旅

同じ命令でも、行き着く先はまったく違います：

![同じgfx::DrawTrianglesがWhisk3D Coreを通り、各バックエンドへ降りていきます：opengl（PC、macOS、N95、Dreamcast、PS Vita）、gles2（Android、ブラウザー、N8、PC）、vulkan（PC）、gu（PSP）、citro3d（3DS）](img/whisk3d-core-despacho.webp)

- **固定機能のOpenGL（PC、N95）：** ほぼそのまま`glDrawElements`へ。行列は描画の直前に、1回の`glLoadMatrixf`でまとめて送ります。
- **OpenGL ES 2.0とWebGL：** 行列のスタックはCPU側にあり、uniformとしてウーバーシェーダーに送られます。WebGLはRAM上の配列を受け付けないので、バックエンドがそれをバッファーに移します。Android 2.3のVideoCore IV GPUでは、状態の組み合わせごとに小さなプログラムを作り、インターフェースの描画をまとめます：1フレームあたり179回だった描画が16回になります。
- **PSP（GE）：** GEは画面の端に対してクリッピングをしないので、CPUが各頂点をクリップ空間に移し、そこでクリッピングします。そのあと、GEが読むリングバッファーにインターリーブ形式で書き込みます。ライト（最大4個）とフォグはハードウェアで処理します。
- **3DS（PICA200）：** 頂点はリニアメモリにコピーされ、独自の頂点シェーダー（`w3d.v.pica`）が変換します。同じ状態で続く小さな描画はまとめて送られます：1フレームあたり191回が18回になります。線と点は、CPU上で三角形として組み立てます。
- **Dreamcast：** GLdcがPVRの上でOpenGL 1.xの役割を果たし、PCやN95と同じ固定機能のバックエンドを独自のパッチ付きで使います。1サイクルも無駄にできないゲームのために`pvr/`があります：GLdcは頂点1つにSH-4のサイクルを約400使いますが、直接描画では1つの命令（`FTRV`）で各頂点を変換します。両方を同じプログラムで使うことはできません。
- **PS Vita：** vitaGLがコンソールのGPU上で固定パイプラインをエミュレートし、実行中にシェーダーをコンパイルします（そのため`libshacccg.suprx`が必要です）。

## バックエンドにできることを尋ねる

すべてのGPUが同じことをできるわけではなく、Coreはそれを隠しません。各バックエンドは自分が持っている機能を答え、描画する側は何かが足りなければ別の方法を選びます。

| 問い合わせ | 「いいえ」のときどうなるか |
|---|---|
| `VBOSoportado()` | メッシュはRAM上の配列として送られます（Dreamcast、Vita） |
| `EstencilBits()` | 水の反射は、クリッピング平面による方法に切り替わります |
| `PlanosRecorteMax()` | 反射はクリッピング平面なしで処理します（PVRにはクリッピング平面がありません） |
| `MezclaTexturasSoportada()` | マテリアルのレイヤーは、複数のパスで描画します |
| `TieneTexGen()` | 球面反射は、ソフトウェアで計算するか、テクスチャ行列で計算します（`TexMatrixMatcap`。こちらはN95でも動きます） |
| `SombreadoPorPixelSoportado()` | ライティングは頂点ごとのままで、エディターはそのオプションを表示すらしません |
| `ShadersEscritos()` | 自作シェーダーを使うマテリアルは、いつもどおりに描画されます（[自作シェーダー](../editor/shaders.md)を参照） |

## 状態のキャッシュ

状態を変えるたびに、ドライバーには何らかのコストがかかります。Coreは現在の設定を覚えていて、すでにオンになっているものをオンにしたり、すでにバインドされているテクスチャをバインドしたりしても、呼び出しは発生しません。`IsEnabled`と`GetMatrix`はGPUに問い合わせず、この記憶から答えます。N95では、そうした問い合わせをすると、描画が終わるまで待たされるからです。

## テクスチャ

`LoadTexture`には2つの段階があります。**デコード**（ファイルからRGBAのピクセルへ）はシステムによって異なり、ほとんどはstb、SymbianではICLを使います。**アップロード**（ピクセルからGPUへ）は共通で、各バックエンドが自分のチップのフォーマットに変換します：

- **PSP：** 512までの2のべき乗、「swizzle」済み、565または8888。
- **3DS：** モートン順の8x8ブロック、1辺8〜1024。
- **Dreamcast：** 8〜1024の2のべき乗、16ビット（565または4444）、ミップマップなし。
- **N95：** 2のべき乗のみ。それ以外はアップロード前にリサンプリングします。

プロジェクトでは、**16ビット**のテクスチャ（メモリは半分）を指定できます。さらにN95でだけ、一定のサイズ以上のテクスチャを**半分のサイズ**でアップロードできます（`texturasMitadDesde`）。`.w3dt`フォーマットは、ミップマップ付きでGPUにそのまま渡せる状態のテクスチャを保存します：読み込みは、読んでアップロードするだけです。

正直に言うと、テクスチャのアップロードとライトは、まだOpenGLの関数を2つか3つ直接呼んでいます。OpenGLのないコンソールでは、それを実装する小さなレイヤーがバックエンドに入っています（`gu/w3dGLgu.cpp`、`citro3d/w3dGLc3d.cpp`）。

## 画面とセーフエリア

`PantallaSetTam`と`PantallaEsVertical`は、画面が縦向きか横向きか（横向き＝高さより幅が大きい）を一度だけ保存し、エンジンのどこからでも問い合わせられるようにします。**セーフエリア**（`SafeAreaGet`）は、各辺の何ピクセルがインターフェースに使えないかを示します：ノッチ、ジェスチャーバー、スマートフォンのブラウザーのバーなどです。背景はウィンドウ全体に描画し、インターフェースはセーフエリアの内側に描画します。PC、Symbian、コンソールでは各辺の値は0で、ブラウザーでは実際に測ります。

## いちばん小さなマシンの制限

Core向けに書くものは、いちばん制約の多いマシンに収まらなければなりません。目に見える制限は次のとおりです：

| 制限 | 場所 | Coreでの対処 |
|---|---|---|
| 16ビットのインデックス（メッシュ1つあたり最大65,535頂点） | Symbian | `MeshIndex`はそこでは16ビット、それ以外では32ビット。インポーターは収まらないものを受け付けません |
| 同時に8個までのライト | すべて（`LucesMax`） | シェーダーのバックエンドは同じ計算でエミュレートします。PSPはハードウェアで4個、Android 2.3は最大4個を使います |
| シェーダーなし | 固定機能のバックエンド | シェーダー関連の関数は「いいえ」を返し、マテリアルはいつもどおりに描画されます |
| 16ビットのZ | PSP | N95と同様に、ニアクリップ面をオービットの距離に合わせて調整します |
| 全部で16 MB | Dreamcast | `-Os`でコンパイルし、リンカーが使わないものを捨てます。テクスチャは16ビットです |
| C++03 | Symbian | ヘッダーでは`nullptr`、`auto`、`override`を使いません（`W3D_OVERRIDE`）。`tools/prueba_independencia.sh`は各ヘッダーを単独で、C++03でコンパイルします |
